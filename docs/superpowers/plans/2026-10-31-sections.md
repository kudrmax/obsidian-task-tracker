# Sections Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A list (Inbox, Soon, Now) can hold `###` sections. A section is made by dropping a task on a zone that names it, tasks and sections move by drag, and an empty section disappears from the screen and from the file.

**Architecture:** The parser stops ending a list at `###`. Inside a list it reads blocks: the headless block at the top, then one block per `###` heading, and records each task's group. Block primitives on `TaskDocument` (add, move, rename, merge, delete) carry the structure. Name-based operations and four new normalization rules sit on top of them. The UI groups the items it already receives by `TaskItem.group`, draws headers, and adds three things: section zones beside the date zones, a name field, and a lifted section.

**Tech Stack:** TypeScript, Obsidian API, vitest (happy-dom for UI tests).

**Spec:** `docs/superpowers/specs/2026-10-31-sections-design.md`. Screens: `docs/design/README.md`, section «Секции» (it wins on looks). Boards: `docs/design/canvas/Sec*.dc.html`.

## Global Constraints

- **Words.**
  - In code, «section» already means a list (`SectionKey`, `settings.sections`).
  - A `###` section is a **group** in code: `GroupName = string | null`, where `null` means the tasks outside any section.
  - The user sees «section» everywhere: «Sections», «New section», «Remove section», «No section».
- **Defaults.** `groups: { presets: ["Morning", "Afternoon", "Evening"], ungrouped: "No section" }`, synced like `priorities` (not a device key).
- **Which lists have groups.** Groups live only in Inbox, Soon and Now. Done, Backlog and the column of another day show none.
- **Where a list ends.** Only at a `#` or `##` heading. `###` starts a group. `####` and deeper are plain text inside the group.
- **Group names.** A name is the heading text after `### `, trimmed, compared case-sensitively. The heading `### <groups.ungrouped>` is the ungrouped group.
- **Text from settings.** Group names from settings are passed in, never written into code or copy.
- **Where `start` and `end` point.**
  - `InsertPosition` `"start"` and `"end"` mean the start and end of the ungrouped group.
  - So New task, the date zones and normalization rules 2–4 land in «No section» without changes of their own (spec §3.4).
- **Contracts in their own commit.** `src/settings.ts` and `src/application/contracts.ts` change in Task 1, in a commit of their own, before anything else.
- **Layers.** `ui` imports `application` only.
- **Styles.** `styles.css` rules read only `var(--tc-…)`. Every new measure in TS goes through `DESIGN` / `DESIGN_TOKENS`. `npm test` runs `tests/styles.test.ts`.
- **Scriptable.** It is built from the same parser. Run `node scriptable/build.mjs` after the parser changes, or `tests/scriptable/build.test.ts` fails.
- **Copy in the same commit.** `src/ui/SettingsTab.ts` descriptions and `README.md` change in the commit that changes behaviour.
- **Branch.** `sections` (worktree `obsidian-task-tracker-sections`). It builds from master and does not wait for `subtasks` (Max's decision).

## Review Focus

1. **A list with `####` lines, plain text and blank lines, inside and between groups.** A read changes nothing. A group holding text but no tasks is kept and not shown.
2. **A task with indented children** moved between groups and lists keeps its children. A `###` straight after a child line ends the children.
3. **Group names.**
   - `### Вечер  ` and `Вечер` are the same group.
   - `Evening` and `evening` are two groups.
   - Renaming to a name the list already has merges the two.
   - Renaming to «No section» hands the tasks to the ungrouped group.
4. **A group renamed or removed in the file between render and action.** The action rejects with `StaleTaskError`, the file is unchanged, and the view refreshes.
5. **The last task dragged out of a group.** The group and its heading go in the same write. If the ungrouped group is all that is left, its heading goes too.

    - an existing name means `moveToGroup` into it;
    - the ungrouped name means `moveToGroup(null)`;

  - `renameGroup(doc, list, from: string, to: string, ungrouped: string)`:

    - when the ungrouped heading exists, `mergeGroup(0, ungrouped, "start")`;
