# The screen's engine first, the connection after

Changes the plan of [`2026-11-16-ui-standard-stack.md`](2026-11-16-ui-standard-stack.md) (Max, 2026-11-18). That spec's goal, stack, architecture rules, «How a feature is checked» and acceptance criteria stay; its stages 1–4 are replaced by the two parts below, and its «Decisions» 2, 5 and 8 (the stage 1 store, scroll refs and «not yet live») are superseded by this spec.

## Why

Stage 1 mixed two jobs: inventing how the screen moves (new animations, drag, gestures) and refactoring the plugin onto it (the hosts, the vault, the old code beside it). Each slowed the other. Now they are separate:

1. **The engine.** The whole screen is built on the stack in a stand plugin, over made-up tasks held in memory, feature by feature, until every part moves the way Max wants. No vault, no tasks file, no old UI in the way.
2. **The connection.** The finished engine is mounted in the plugin over the real tasks file, and the old UI is deleted. This is the refactor, with nothing left to invent.

## Part 1: the engine

### What it is

Presentation only: React components, the screen's store, the gestures, the motion, in `obsidian/ui/engine/`. It decides no product rule (`CLAUDE.md`, «The UI decides nothing»).

- **Rules are the real core's, from the first day.** The engine imports `core/application/contracts.ts` exactly as `obsidian/ui` does today: its types and its pure rules (`swipeLanding`, `dividerAt`, `stackedLists`, `levelAt`, `placeAt`, `acceptsDrop`, `gridAt`, …), called directly on every pointer frame. There is no second rulebook to reconcile later.
- **Made-up tasks, real services.** The stand composes the real core (`composeCore`: `TaskService`, `DayService`, `UndoService`) over an in-memory tasks file (`tests/fakes/InMemoryTaskFileStore`), a settable clock and fake calendars. A write waits an artificial delay like a real write and read-back (default 30 ms; 0 and 300 ms selectable), because drop animations depend on that timing.
- **The store** is stage 1's `screenStore.ts` over those services, moved into the engine. Nothing is parked: in part 2 only what it is composed over changes.
- **Mock data**: the ~300-task generator of stage 0 and stage 1 writes the in-memory file, with every case on screen: sections, empty sections, nested subtasks, folded cards, projects and folders, due dates, timed and long tasks, overlapping blocks, all-day and timed events, overdue.
- **States the stand sets by hand**, which the engine draws from the core's reads, are checked end to end only in part 2: the missing file (F6), an outside edit or Sync (F7), the plugin's reload (F8), calendar refresh triggers and source states (F109, F273), «Can't undo: the tasks file changed» (F270), Google notices (F272), no model served (F266).

### The stand

`obsidian/stand/`: a plugin of its own for the test Obsidian only.

- **Build:** its own esbuild entry, `manifest.json` with the id `task-calendar-stand` and its own `main.js`, kept out of the root, so `npm run release` and BRAT never see it. It takes the root `styles.css`.
- **No clash with the plugin:** its own view type and note code block language; the real plugin is disabled in the stand's vault.
- **Guards:** `tests/architecture.test.ts` gets a `stand` layer that may import `ui`, `contracts.ts`, `composeCore` and the fakes; nothing imports `stand`.
- **Hosts:** it opens the engine's screen in a leaf, in a note block, in a pop-out window and in the phone view, as the plugin will.
- **Variants:** a design variant Max is to choose between is a switch in the stand's own code, never in `obsidian/ui/engine`, and is removed once he decides.
- **The real plugin** keeps the old UI mounted during part 1; stage 1's mount of the new screen into the plugin's hosts is undone in E0 and comes back in part 2.

### Checks

The old spec's «How a feature is checked», applied to the stand:

- The harness (`tests/e2e/`) takes the plugin id and the screen's root selector as settings and runs on the stand.
- The oracle keeps reading the tasks file's text, now from the in-memory file (`window.__tcStand.fileText()`), with the same parser, so a scenario never asks the engine what it did.
- Every scenario of part 1 runs again unchanged in part 2, on the plugin with a real tasks file.
- Each milestone re-runs the scenarios of the milestones before it.

### Design is open

Max, 2026-11-18: the stand's motion is much better than the released screen's, so the design may change where the motion makes a part of it unneeded. A visual change is Max's decision. It reaches him as a working variant on the stand, never decided by an agent. Each change he decides is drawn into `docs/design` (README and the board) in the same milestone, and `docs/plugin/` follows in that branch (`CLAUDE.md`, «The screen is decided»).

Decided:

1. **No purple line between cards** (replaces F150's bar and F177's line for the plus). While a card is carried, the cards under it part smoothly and the gap is where it will land, as on the stage 0 stand. The gap shows the card's place outline at the depth it will take: a subtask's is indented by its level. The look is dnd-kit's documented sortable tree; the place and the depth are the core's (`placeAt`, `levelAt`), never computed in the component. A refused place opens no gap, and the gap stays where the card was lifted.

Not decided, shown as variants when their milestone comes:

- the timeline's drop line (stage 0 drew the landing block instead);
- the dashed place left behind (F147);
- the outline around a parent.

The iPhone app keeps its design until Max approves the new one in the plugin; carrying it there is a task of its own after part 2.

## Part 2: the connection

1. `origin/master` is merged in; what it added to the old UI joins the feature list. The store is composed over the plugin's real services (the vault's tasks file, the calendars, the device's settings) instead of the in-memory ones. A need the core cannot answer yet goes to `backend` first (`contracts.ts` changes only with the whole team).
2. The plugin's hosts (the leaf, the note block) mount the engine. The old UI goes (`trash`), and the lint rule of the old spec's acceptance criteria is added.
3. Every part 1 scenario runs again unchanged on the plugin, then the part 2 features above get their scenarios.
4. `docs/plugin/` follows every behaviour or look that changed.
5. The old spec's acceptance criteria, then the release. Before it, the trackpad pager is re-checked with Max and an issue is opened for what remains («~95 %»).
6. The stand stays as the engine's test bed until Max says to remove it.

## Branches

Part 1 continues on `ui-standard-stack` (stage 1's commits are its start). The engine is built apart from the plugin, so part 1 never merges `origin/master` (Max, 2026-11-18). Master is merged once, at the start of part 2; the behaviours master added to the old UI by then join the feature list there. `spike-stage0-tried` and `ui-stack-spike` (the stage 0 stand) stay until Max says to delete them; he compares them with the result.
