# The screen's engine first, the connection after

Changes the plan of [`2026-11-16-ui-standard-stack.md`](2026-11-16-ui-standard-stack.md) (Max, 2026-11-18). That spec's goal, stack, architecture rules, «How a feature is checked» and acceptance criteria stay; its stages 1–4 are replaced by the two parts below, and its «Decisions» 2, 5 and 8 (the stage 1 store, scroll refs and «not yet live») are superseded by this spec.

## Why

Stage 1 mixed two jobs: inventing how the screen moves (new animations, drag, gestures) and refactoring the plugin onto it (the hosts, the vault, the old code beside it). Each slowed the other. Now they are separate:

1. **The engine.** The whole screen is built on the stack in a stand plugin, over made-up tasks held in memory, feature by feature, until every part moves the way Max wants. No vault, no tasks file, no old UI in the way.
2. **The connection.** The finished engine is mounted in the plugin over the real tasks file, and the old UI is deleted. This is the refactor, with nothing left to invent.

## Part 1: the engine

### What it is

The screen's mechanics, apart from the core: React components, the screen's store, the gestures, the motion, the layout, in `obsidian/ui/engine/`. **It imports nothing from `core/`** (Max, 2026-11-18). The core's screen rules were written for the old UI and are part of what this work replaces, so the engine does not inherit them.

- **One port.** `obsidian/ui/engine/port.ts` (`ScreenPort`): the screen's data in the engine's own types, shaped by what the screen draws (columns, sections, cards, the day's blocks and events, menus as ready lists); a subscription to its changes; the writes (move to a place, drop at a time, resize, add, edit, a menu choice, undo…). It grows milestone by milestone.
- **Mechanics are the engine's.** Where a card lands under the pointer, at which depth, how the ribbon pages, widths, snapping, stacking blocks: pure, unit-tested modules in `obsidian/ui/engine/` (not inside components), written fresh for the new screen. They are the screen's geometry, not product rules. The two behaviours Max had to ask for twice (`CLAUDE.md`) hold in the engine too, each guarded by the engine's own test naming him: one swipe moves the ribbon one place, from the first swipe; at Inbox and Soon the two columns split the screen in half.
- **Product rules sit behind the port.** What a drop writes, which places refuse a task, where a new task goes, what a menu offers: the engine asks the port and draws the answer, never decides itself.
- **`MockPort`** (the stand's): simple made-up tasks in memory with the simplest product rules that make each case appear (a refused place, a subtask, a section, a timed task, an overdue one). Writes are asynchronous with a delay like a real write and read-back (default 30 ms; 0 and 300 ms selectable), because the drop animations depend on that timing. Its state reads as a tasks file's text (`window.__tcStand.fileText()`), so the checks' oracle reads what was «written» without asking the engine.
- **Mock data**: a generator of ~300 simple tasks with every case on screen: sections, empty sections, nested subtasks, folded cards, projects and folders, due dates, timed and long tasks, overlapping blocks, all-day and timed events, overdue.
- **Stage 1's code** is taken where it fits (components, the trackpad pager `wheelStrokes.ts`, the harness), rewritten onto the port; its store over `TaskService` and its calls into the core are left out.
- **States the stand sets by hand** through `MockPort`, checked end to end only in part 2: the missing file (F6), an outside edit or Sync (F7), the plugin's reload (F8), calendar refresh triggers and source states (F109, F273), «Can't undo: the tasks file changed» (F270), Google notices (F272), no model served (F266).

### The stand

`obsidian/stand/`: a plugin of its own for the test Obsidian only.

- **Build:** its own esbuild entry, `manifest.json` with the id `task-calendar-stand` and its own `main.js`, kept out of the root, so `npm run release` and BRAT never see it. It takes the root `styles.css`.
- **No clash with the plugin:** its own view type and note code block language; the real plugin is disabled in the stand's vault.
- **Guards:** `tests/architecture.test.ts` gets an `engine` rule (imports nothing from `core/`) and a `stand` layer that may import the engine; nothing imports `stand`.
- **Hosts:** it opens the engine's screen in a leaf, in a note block, in a pop-out window and in the phone view, as the plugin will.
- **Variants:** a design variant Max is to choose between is a switch in the stand's own code, never in `obsidian/ui/engine`, and is removed once he decides.
- **The real plugin** keeps the old UI mounted during part 1; stage 1's mount of the new screen into the plugin's hosts is undone in E0 and comes back in part 2.

### Checks

The old spec's «How a feature is checked», applied to the stand:

- The harness (`tests/e2e/`) takes the plugin id and the screen's root selector as settings and runs on the stand.
- The oracle reads `MockPort`'s state as a tasks file's text (`window.__tcStand.fileText()`), with the same parser, so a scenario never asks the engine what it did.
- Every scenario of part 1 runs again unchanged in part 2, on the plugin with a real tasks file.
- Each milestone re-runs the scenarios of the milestones before it.

### Design is open

Max, 2026-11-18: the stand's motion is much better than the released screen's, so the design may change where the motion makes a part of it unneeded. A visual change is Max's decision. It reaches him as a working variant on the stand, never decided by an agent. Each change he decides is drawn into `docs/design` (README and the board) in the same milestone, and `docs/plugin/` follows in that branch (`CLAUDE.md`, «The screen is decided»).

Decided:

1. **No purple line between cards** (replaces F150's bar and F177's line for the plus). While a card is carried, the cards under it part smoothly and the gap is where it will land, as on the stage 0 stand. The gap shows the card's place outline at the depth it will take: a subtask's is indented by its level, as dnd-kit's documented sortable tree does. The place and the depth come from the engine's drop geometry module, never computed in a component; whether the place accepts the task is asked of the port. A refused place opens no gap, and the gap stays where the card was lifted.

Not decided, shown as variants when their milestone comes:

- the timeline's drop line (stage 0 drew the landing block instead);
- the dashed place left behind (F147);
- the outline around a parent.

The iPhone app keeps its design until Max approves the new one in the plugin; carrying it there is a task of its own after part 2.

## Part 2: the connection

1. `origin/master` is merged in; what it added to the old UI joins the feature list.
2. **The core is audited against the engine.** Each `core/application` module is sorted: still needed behind the port (the file, the tasks, writes, undo, calendars, product rules), replaced by the engine's own mechanics (the old screen geometry: drop lines and landing, carry and lift, layout widths, stacked rows, zoom and snap…), or dead. The iPhone app runs on the same core: a module it still uses stays until the app moves too, and that is named in the audit. Max sees the audit's result before anything is deleted from the core.
3. `CorePort`: the port over the core's services, in `obsidian/`. A product rule `MockPort` had and the core lacks goes to `backend` first (`contracts.ts` changes only with the whole team).
4. The plugin's hosts (the leaf, the note block) mount the engine over `CorePort`. The old UI goes (`trash`), and the lint rule of the old spec's acceptance criteria is added.
5. Every part 1 scenario runs again unchanged on the plugin with a real tasks file, then the part 2 features above get their scenarios.
6. `docs/plugin/` follows every behaviour or look that changed.
7. The old spec's acceptance criteria, then the release. Before it, the trackpad pager is re-checked with Max and an issue is opened for what remains («~95 %»).
8. The stand stays as the engine's test bed until Max says to remove it.
