# The plugin's screen, rebuilt: one mechanism per concern, on the standard stack

Issue: kudrmax/obsidian-task-tracker#41. This is the one spec of the rework. It gathers what held up in every earlier attempt and replaces them:

- [`2026-11-16-ui-standard-stack.md`](2026-11-16-ui-standard-stack.md): the stack and how a feature is checked;
- its [feature list](2026-11-16-ui-standard-stack-features.md) (F1–F310), which stays the scope;
- [stage 0's results](ui-standard-stack/stage0.md), which stay the reference for using the libraries;
- the old refactor spec, revision 15 (branch `ui-refactor-spec11`, `docs/superpowers/specs/2026-11-15-ui-refactor.md`): its root cause, its principles, its rule that each concern is built once, and the reason four earlier attempts failed.

## Why

Max uses the screen every day, on the phone and on the Mac. It must:

- show no visual bugs: no card jumping, doubling, flickering or landing in the wrong place;
- move smoothly: every card that changes place glides there, the same way every time;
- never lag, with a real file of a few hundred tasks;
- behave the same everywhere: the main screen and the block in a note, phone and desktop.

**The bugs have one root.** The old UI has no single owner for anything it does. Its count, from reading every file:

- 4 drag loops, about 8 motion paths, about 9 owners of focus, about 14 key handlers, 2 text-entry engines;
- the place (main screen or note) read in about 10 branches;
- the shown day kept in 9 places, the ribbon's position in 11;
- 84 places that read sizes from the live page, often mid-animation.

Every fix had to be made once per copy, and the copies disagreed. That is the jumping, the doubling, the cards flying on a filter change, the redraw under the finger.

**Why the earlier attempts failed.** Four specs said «one mechanism» and still produced copies, for one reason. The work was sliced by place or by feature, and each slice built the whole mechanism it needed for itself. Nothing named the one owner every slice had to use. The checks tested behaviour, which two correct copies both pass. Then revisions 12–15 tried to prevent copies with ever more machinery of their own (a type system against a deliberate saboteur, own engines for render, motion and input). That became an arms race with endless review loops, and it was stopped.

**The fix, as one sentence.** Every concern of the screen has exactly one owner in the code. The owner is a standard library used the standard way, wrapped once. Every place and every feature reaches the concern only through that owner. The skeleton of owners is built first, and the features plug into it.

## Principles

1. **One screen, one state, one direction.** The whole UI is one React tree, `TaskScreen`, over one store per mounted screen. What the screen shows is a function of the store's state. A user action calls an action, the action writes through the port, the new data comes back into the store, and React redraws. The page is an output; nothing reads truth back from it. The main screen and a note's block are the same `TaskScreen` with a different `place` prop, read in one module only.
2. **One owner per concern** (the table below). A feature that needs a concern uses its owner. A feature that seems to need a second way of doing the same thing changes the owner's configuration, never adds a path beside it.
3. **Motion follows the change, not its cause.** A card moves only because its place in the state changed: a drag, Undo, a command, Sync, a new task all give the same animation. A change of context (another project, mode, filter) draws in place; no card flies: the context is the React `key` of the list's region, so a new context mounts without layout animation, and nothing else suppresses motion. A day or ribbon change is one whole-region transition.
4. **Sizes are the browser's.** Layout is CSS. Where a library needs sizes (the virtualizer, dnd-kit) it measures them itself. No component measures or moves an element by hand.
5. **What the finger holds stays still under it.** While a drag runs, the layout under it is dnd-kit's. Data that arrives meanwhile waits in the store and is applied at the drag's end or cancel: the store's one exception to applying at once. The dragged task is never removed under the finger.
6. **The UI decides nothing.** What a drop writes, which places refuse a task, where a new task goes, what a menu offers: the screen asks the port and draws the answer (`CLAUDE.md`, «The UI decides nothing»). The screen's own job is drawing and turning gestures into places and minutes.
7. **Everything alive has an owner.** A subscription, an observer or a timer lives inside the hook that owns its concern and ends with it. A screen unmounted mid-gesture leaves nothing behind.
8. **Performance is the architecture's, not a later tuning.** A card re-renders only when its own data changed: selectors, structural sharing and a memoized card face. Long lists are virtualized. The budget is no main-thread task over 16 ms on any interaction with ~300 tasks, phone view and desktop. Lifting a card is the one exception, under 33 ms: stage 0 showed that no drag library used as documented lifts within one frame.
9. **Standard, never invented** (Max: «ЗАПРЕЩАЮ что-либо придумывать», «ищи существующие нормальные решения»). Each owner is a library's own feature or its documented pattern, never one particular app's solution. Code of our own is only the glue a library leaves to the app, and each piece names the standard it follows.

## How the owners are kept one

Against ordinary development, not sabotage. Three tiers, from the old spec's threat model, without its machinery:

1. **By construction.** The skeleton is built first (E0), so a feature finds its concern's owner already there. The owner is the shortest way to do the job.
2. **By machine.** The table is data in `tests/architecture.test.ts`. A failing test catches every natural route to a copy:
   - a library imported outside its owner: dnd-kit only in `engine/drag`; @use-gesture only in `engine/gestures`; Floating UI only in `engine/layers`; Motion only in `MovingRow`, `Slide` and the ribbon's own files (`FollowRibbon.ts`, `RibbonTrack.tsx`, `dayChange.ts`), `animate(` in `FollowRibbon.ts` alone; TanStack Virtual only in the list component; Zustand only in `engine/store`; Obsidian's editor and CodeMirror only in `ObsidianEditor`;
   - a second `DndContext`;
   - a component touching the page by hand: `addEventListener`, `getBoundingClientRect` or any size or scroll read, `animate(`, `requestAnimationFrame`, a timer (the store's minute tick and the counted few apart), a clock read (time is the port's), the focus moved outside the layers; each exception named and counted with its reason;
   - the engine importing anything from `core/`;
   - a task field compared in the view (`tests/uiDecides.test.ts`).

   The guards are in the first commit of the engine, before any feature.
3. **By review.** Each milestone ends with one review by an agent that did not write the code. Its first question: did any concern get a second path? A copy found is fixed in the owner, and the fix is checked by its scenario, not by another review round. jscpd runs as a backstop on copied code.

## The engine apart from the plugin (Max, 2026-11-18)

Inventing how the screen moves and refactoring the plugin onto it are two jobs; mixed, each slowed the other. They are done one after the other.

**Part 1: the engine,** on a stand plugin over made-up tasks: the skeleton and the main features, for how the screen feels. No vault, no tasks file, no old UI in the way.

- **The engine** lives in `obsidian/ui/engine/` and imports nothing from `core/`. The core's screen rules were written for the old UI, and this work replaces them.
- **`MockPort`**, the stand's port:
  - simple made-up tasks in memory, with the simplest product rules that make each case appear (a refused place, a subtask, a section, a timed task, an overdue one); they exist only to make cases appear, and in part 2 the core's rule wins;
  - writes are asynchronous, with a delay like a real write and read-back (default 30 ms; 0 and 300 ms selectable), because the drop animations depend on that timing;
  - its state reads as a tasks file's text (`window.__tcStand.fileText()`), so the checks' oracle never asks the engine what it did.
- **Mock data:** ~300 simple tasks with every case on screen: sections, empty sections, nested subtasks, folded cards, projects and folders, due dates, timed and long tasks, overlapping blocks, all-day and timed events, overdue.
- **The stand,** `obsidian/stand/`, is a plugin of its own for the test Obsidian only:
  - its own esbuild entry and `manifest.json` (id `task-calendar-stand`), kept out of the root so `npm run release` and BRAT never see it, with the root `styles.css`;
  - its own view type and note code block language; the real plugin is disabled in its vault;
  - it opens the screen in a leaf, a note block, a pop-out window and the phone view;
  - a design variant Max chooses between is a switch in the stand's code only, removed once he decides.
- **The real plugin** keeps its old UI during part 1. `origin/master` is not merged during part 1.

**Part 2: the connection.**

1. Merge `origin/master`; what it added to the old UI joins the feature list.
2. **Audit the core against the engine.** Sort each `core/application` module: still needed behind the port (the file, the tasks, writes, undo, calendars, product rules); replaced by the engine (the old screen geometry: drop lines and landing, carry and lift, layout widths, stacked rows, zoom and snap); or dead. The iPhone app runs on the same core, so a module it uses stays until the app moves too. Max sees the audit before anything is deleted from the core.
3. `CorePort`: the port over the core's services, in `obsidian/`. Where the core has a rule, the core's rule is used. A case the engine draws and the core has no rule for is a product question for Max; once he answers, it goes to `backend` (`contracts.ts` changes only with the whole team).
4. The plugin's leaf and note block mount the engine over `CorePort`. The old UI goes (`trash`), with no flag between old and new.
5. Every part 1 scenario runs again unchanged on the plugin with a real tasks file. Then the rest of the feature list is built on the engine's owners, with its scenarios, including F6–F8, F109, F266, F270, F272 and F273 (the file, Sync, calendar sources, notices) and F300 (settings rows on the one drag owner).
6. `docs/plugin/` follows every behaviour or look that changed.
7. The acceptance criteria below, then the release. Before it, the trackpad pager is re-checked with Max and an issue is opened for what remains («~95 %», with his recordings).

## How a feature is checked

A feature is checked the way Max uses it, in motion, never by numbers the code under test computes about itself. Stage 0 passed a timeline that teleported, flickered and dropped tasks at the wrong hour, because the check compared the code's own pixel-to-minute math with itself.

1. **Scenario first.** Before a feature is built, it gets an end-to-end scenario in the test Obsidian: real gestures at human pace (slow, fast, back and forth, released outside a target, repeated), driven over CDP. It fails before the code exists.
2. **The oracle is what the user sees and means,** read apart from the code: the label or line under the pointer, the card's text on screen, the tasks file's text. Dropped under «09:00» means the file says 09:00 and the block's top is on that line.
3. **Frame checks on a screencast of every frame:**
   - what is under the finger is visible and follows it;
   - nothing vanishes, flickers, doubles or jumps further than the gesture moved;
   - zoom keeps the time under the pointer;
   - no stray selection or highlight;
   - text is never cut mid-line.
4. **The states the user reaches:** zoomed, scrolled to the edges, a pop-out window, the phone view, light and dark.
5. **Real input.** Max's recorded trackpad and pointer streams are replayed in every run; every new recording joins the set.
6. **Someone else looks.** An agent that did not build the feature watches the recordings and frames to find defects, not to confirm.
7. **A defect Max finds** first gets a check that catches it, then the fix.
8. **Earlier milestones' scenarios** run again at every milestone.

## Decisions

Gaps decided while building, recorded here (`CLAUDE.md`, «Agents»). Technical choices stay with the agents; only a product question reaches Max, in product words.

### E0 (frontend-obsidian, 2026-11-18)

1. **Motion in the gestures too.** The table's gestures row lets go into Motion springs, so the guard allows Motion in `engine/gestures` besides `MovingRow` and `Slide`; `animate(` is allowed there only. Standard: Motion's `animate` on a `MotionValue`.
2. **The ribbon is CSS percent.** The strip is `STRIP_WIDTH` % of the window, each column `COLUMN_SHARE` % of the strip (`engine/layout/columns`), and the strip slides by its own percent: nothing is measured to place it. Standard: CSS widths and transforms.
3. **The ribbon's page width under a finger** is the ribbon's `clientWidth`, read as the finger begins (in `bounds` and the release). Standard: @use-gesture's pager example reads the page width the same way.
4. **A finger's swipe lands by @use-gesture's own `swipe`** (its velocity and distance) or past half a column, never two stops (`swipeStep`). Standard: the usual pager rule, @use-gesture's swipe detection.
5. **The ribbon's drag follows the pointer on the view's window, not by capture** (`pointer.capture: false`): a long press on a card can hand the pointer to the drag mid-swipe, and the ribbon's gesture still ends. Standard: @use-gesture's documented `pointer.capture` option.
6. **A drag always takes the gesture slot.** Its activation constraint (a long press held within 5 px, or the mouse past 4 px) already proved no other gesture moved; the ribbon reads the slot through `enabled`. Standard: dnd-kit's activation constraints, @use-gesture's `enabled`.
7. **A drop is drawn at once from `port.preview`, and reads wait until its write is read back**, as they wait during the drag (principle 5 extended to the drag's own write). Standard: optimistic updates with outgoing reads held during the mutation (TanStack Query's optimistic-update guide).
8. **A sortable drop's place is `arrayMove`'s**: before the task that follows the card in the new order, the list's end after the last; the port puts it in that task's section and under its parent. Drops over another list wait for E1. Standard: dnd-kit's sortable `onDragEnd` with `arrayMove`.
9. **A menu's items reach the view through the store** (`layer.items`, asked of the port as the menu opens): the port has one user, the store. Standard: the port behind the store (hexagonal).
10. **Rows leave at once in E0.** Every row that leaves is gone in the same frame (a moved task glides in at its new place by its layout id); fading out a task gone from the screen comes with E2's cards leaving. Standard: Motion's `AnimatePresence` `popLayout`.
11. **The timeline opens on the now line by the browser's `scrollIntoView`**, the reveal of a scroller that is not a virtual list; the guard allows it in `view/Timeline.tsx` only. Standard: the DOM's `scrollIntoView`.
12. **The hour label under the now pill is hidden** by the time scale's own geometry (`TimeScale.NEAR_NOW`, the design's label lift and pill), as the released screen hides it; the core's `labelHidesNearNow` is not imported. Standard: the design's measures (`DESIGN`).
13. **Blocks that overlap stand side by side in lanes the port gives** (`Block.lane`, `lanes`; MockPort's simplest rule: the first lane free at the block's start), and a short block is still a whole card tall (the released screen's stacked cards). Standard: the port decides, CSS draws (`--tc-x`, `--tc-x-end`).
14. **A card's colour is the host's paint**: the card carries the port's colour as `data-priority`, the host paints those rules (`showPriorityColors`). Standard: the table's «Haptics, theme, platform» row: the host passes tokens.
15. **The keys of E0 are ← and →**, one stop as a stroke goes, on the view's `Scope` and as commands; they do nothing while a layer, a field or a gesture holds the screen (`takesKeys`). Standard: Obsidian's `Scope` and commands.
16. **Quick add in E0** is the plus opening a field over the screen's foot (`tc-quick-bar`) that holds `ObsidianEditor`; Enter adds where the port puts new tasks (MockPort: the top of Inbox), the list reveals it by `scrollToIndex`, the field closes; Escape closes it. E4 designs the real one.
17. **The stand's note block** shows Inbox in a fixed room (`--tc-stand-block-h`), the same `TaskScreen` with `place="note"`.
18. **Chromium's touch slop.** In the desktop's phone view Chromium sends a finger's `touchmove` only once it has gone about 15 px, so on a card a finger slower than that per 250 ms reads as dnd-kit's long press and lifts the card. iOS sends every move, so dnd-kit's 5 px tolerance holds there: this is checked on the iPhone with Max (the blocker stage 0 left open). The emulated slow-swipe checks start on a column's head.
19. **Pop-out windows are not run in E0's checks**: opening one puts a window on the person's screen. The overlay's portal and Floating UI's root are the view's own document, as stage 0 checked.
20. **A layer stands over the design's backdrop** (`tc-backdrop`, drawn by Floating UI's `FloatingOverlay`): the panel's colour is slightly translucent by design and lets the cards' text through without it. In E0 the backdrop blurs the card the menu opened from too; E4's task menu lifts it above. Standard: Floating UI's `FloatingOverlay`; `useDismiss` closes on a press on it.
21. **Recorded wheel input is replayed at its recorded times** (CDP's `timestamp` on each event), so the page's pager reads the person's timing, not the replay loop's jitter. Standard: CDP `Input.dispatchMouseEvent`.

### Steps on the stand (lead, 2026-11-18, Max's decisions)

22. **A subtask by swipes, not by where the hand is** (Max). On a new place the carried card is a task of the row below it (on its own place, its own level). Once the hand rests there a moment (`SWIPE_REST_MS`), each `SWIPE_STEP` (20 px) swiped right is one level deeper, left one shallower, as far as the place allows; the way the hand came there counts for nothing, and a swipe past what the place allows builds nothing up. One rule, `SwipeLevel` in `engine/drag/tree.ts`, for a card in place, a card carried elsewhere, another column and the plus. Replaces the sideways shift from the lift point (a fixed third of the list, then a sticky 40 px step), which Max found to feel like two logics.
23. **An empty section is its header alone** (Max). No «No tasks» plate: under an empty section's header the card's place opens as it does anywhere, and nothing goes away at the drop. Replaces the plate the card's place took over.

    - **Where a menu opens from** is one record in the layers, written by one opener, `useMenuFrom()(id, from, element,
      look, reveal)`: the element comes from the press itself (`pressedIn`, the row's own element), never from the
      document; a calendar block's copy gets the block's look from the opener (the store holds no element and no look).
      A hold let go unmoved (F106, the mouse's long tap) opens the menu through the row's own tap, which dnd-kit carries
      as the sortable's `data.press`, with `held` (no reveal, no scroll into sight, as before).
    - **A menu over a task no longer shown** closes, in a read as in another context (`menuOver`), with a field typed in
      its stack; a kept menu shows its task as the read has it. A test port must read a task back under the fresh id its
      write answers, as the core does.
    - **A tap in the menu is written once the layer says it has faded out** (`MenuLayer`'s `onGone`, Floating UI's
      transition status, or the layer taken off first; the store's `layerGone`); a screen stopping writes it at once.
    - **The bar** is the store's state (`bar`), worked out again in the same change only when the field, the draft, the
      text or the read changes; `offers()` and the views read it.
    - **What each stop shows** is said once, by the layout: `columnsOf(place, stop)`; `reachOf` and `stopShowing` (the
      stop that brings a list into sight: the same while it shows it, else the last of the lists' own stops) are built on
      it; `Stop` and `Place` live in `layout/columns.ts`.
    - **A selected task's dots** follow it every frame only while it moves: its box gliding (the browser's transition
      events on the block's row), a dot pulled, or the ribbon, a pinch or the divider moving the screen; standing, Floating
      UI's observers move them. The ribbon's landing after a lift is followed by `autoUpdate`'s layout-shift watch.
    - **The sensors** (`drag/sensors.ts`) are dnd-kit's own over their public constructors: the mouse's constraint by what
      it presses (a card `{delay, distance}`, started once: dnd-kit leaves the delay's timer running once the distance
      started it, and started the drag twice; empty time `{delay, tolerance}`; the plus `{distance}`); the touch's long press
      composed over `TouchSensor`, forgotten when the screen's root hears a second finger (`useTouchPresses`; the old
      sensor heard it on the whole document, the root hears it on the screen); the root also keeps a carried touch's
      lift from sending a click. The divider holds the pointer against a drag (`holdsPointer`).
    - **Each screen's rows are named apart** (`RowScreen`, React's `useId`): Motion keeps one register of layout ids for the
      window, so a note's block beside the main screen hid the main screen's cards of the same tasks (found by
      `e25-menu-origin`, fixed here).
    - **The ribbon's drag** leaves taps unfiltered by @use-gesture's default (`filterTaps` off) with its threshold kept at
      3 px, as `filterTaps` had it; the ribbon's and the calendar's drawn widths are read in one place (`drawnWidths`).
    - **The guard** counts its exceptions with their reasons (`BY_HAND_EXCEPTIONS.why`): the zoom's reads of its room,
      the drawn widths, the store's minute tick and the scroll's quarter second (F162: dnd-kit's auto-scroll has no delay),
      the tick's alignment to the clock's minute, a sideways swipe's pace. The row's estimate is `cardHeight + cardGap`
      (the list's gap, 2 px as `itemGap`).

      the layout's (`--tc-stack-z` from `layTasks`' rank; the DOM order by id plays no part). On `CorePort` the step's tasks
      come with new ids, so the old blocks fade out and the new fade in, and they did so a second late: the checks' clock

144. **The trackpad module made safe to ship** (frontend-obsidian, 2026-11-22; the plan's step 6, the risk review's
    points a–f; corrects Decision 126's «once per process», «the plugin's folder» and «nothing to turn it off»). What Max
    sees: nothing new while it works; a switch «Trackpad through macOS» (on by default; off, the ribbon reads the
    trackpad by `WheelFollow`, as without the module) and, only after Obsidian quit while loading the module, one notice
    saying it is off and how to try it again. Decided here: (1) **One entry**,
    `trackpadFingers(app, plugin): Promise<MacTrackpadFingers | null>` in `obsidian/infrastructure/trackpad/index.ts`, the
    only way in for the plugin and the stand: null on the phone, on Windows and Linux, with the switch off, or wherever
    the module can't load; the module's code (Node's `crypto`, `fs`, `path`) is imported only past that check, so the
    phone never asks for Node (`trackpad.test.ts` bundles the entry as esbuild builds `main.js` and runs it where Node's
    modules throw). It ends with the plugin (`plugin.register`) and with the window's page (`pagehide`); `dispose` is
    idempotent. (2) **A new build takes over the running hook.** The hook is shared by every build in the process: the
    first keeps AppKit's own `-[NSEvent deltaY]` and `-[NSWindow sendEvent:]` under marker selectors
    (`taskCalendarTrackpadOriginal…`) and the hook in force under `taskCalendarTrackpadHook…`; a build's `take()` puts its
    own functions over AppKit's originals when the hook in force is still ours («fresh» or «tookOver»), and refuses when
    something else hooked over it (or a stage-0 build with the old marker runs). `take()` is called each time a build
    becomes the current one, so a revert to a build loaded before (the release plan's rollback) takes the hook again;
    found live: a build `require`d a second time came back from Node's cache without hooking, and the signals stopped.
    The main process keeps one registry for every loader (`Symbol.for("task-calendar.trackpad.registry")`, shape 1): the
    current build, the windows listening (each with its own loader's sender, so two windows of different plugin
    versions each get their own format), the files loaded. The build before is stopped as the new one takes the hook.
